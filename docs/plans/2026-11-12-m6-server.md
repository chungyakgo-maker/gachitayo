# M6 계획: 서버 (Supabase, 파일 게이트웨이, 동기화, 깨우기)

사양서 4장(서버·파일·CI), 5.4-4, 6.4 uploadQueue, 6.5 표, 6.6 파일 게이트웨이, 8.1 첫 실행, 8.8 동기화 상태, 9장(통신·서버 오류), 10.1 게이트웨이 테스트, 11장.

## 정한 것
- 서버 설정값(`VITE_SUPABASE_URL` 등)이 아직 없으면 앱은 지금처럼 폰에만 저장하고, 첫 실행의 계정 만들기도 건너뛴다. 설정한 뒤 배포하면 그때부터 계정을 만들고 올린다.
- 토큰 검증은 두 방식을 모두 지원한다: 비대칭 키(JWKS, ES256/RS256)는 자동, 예전 대칭 키(HS256)는 `SUPABASE_JWT_SECRET` 비밀값을 등록하면 쓴다. 사용자는 어느 방식인지에 따라 비밀값 등록 여부만 정하면 된다.
- Worker는 `worker/` 폴더의 별도 패키지다. Cloudflare의 Workers용 Vitest 환경(@cloudflare/vitest-pool-workers 0.23.0)이 Vitest 4만 지원해서 앱(Vitest 5)과 나눈다.
- Worker 설정값 `SUPABASE_URL`, `ALLOWED_ORIGIN`은 `wrangler.toml`에 적지 않고 배포 때 GitHub Actions 변수에서 넣는다 (사용자가 파일을 고칠 필요가 없게). `ALLOWED_ORIGIN` = `https://{저장소 주인}.github.io`.
- Cloudflare 비밀값이 아직 없으면 Worker 배포 단계는 건너뛴다 (CI가 실패하지 않게).
- 세션 업로드 순서: 코스 → 원본·처리된 궤적 파일(PUT, HEAD로 크기 확인) → 세션 행 → 랩 행. 다시 처리해서 랩이 줄었으면 남는 랩 행은 지운다.
- 첫 주행에서 코스를 저장하지 않은 세션도 올린다(`course_id` null). 나중에 코스를 저장하면 다시 올려 연결한다.
- 업로드가 끝나고 7일 지난 원본 덩어리는 폰에서 지운다 (사양서 6.4). 결과·요약은 남는다.

## 작업
1. Worker: 경로 검사, 토큰 검증(JWKS 캐시, 만료·발급자), 403/404/413, CORS·OPTIONS, PUT/GET/HEAD. 테스트: 사양서 10.1 목록 전부.
2. 앱: supabase-js, 익명 계정·닉네임(profiles), Dexie v3 `uploadQueue`, 동기화 엔진(지수 백오프, 통신 복구·앱 시작·처리 뒤·1분마다), 파일 만들기(원본은 기존 형식, 처리된 궤적은 열 단위 JSON.gz).
3. 화면: 첫 실행(닉네임, 홈 화면 추가 안내, 안전 안내), 설정(닉네임, 동기화 상태·다시 시도, 익명 계정 안내), 메인 업로드 대기 한 줄, 요약 업로드 상태, 서버 점검 중·계정 끊김 안내.
4. CI: Worker 타입 검사·테스트, main이면 Worker 배포. `supabase-keepalive.yml`(3일마다 + 수동).
5. 사용자 설정 안내와 SQL(채팅).

## 완료 확인
- 앱·Worker 테스트, 타입 검사, 빌드, CI.
- 사용자 설정 뒤: 폰에서 첫 실행 → 주행 → 요약에 "업로드됨", Supabase 표 편집기에 세션·랩 행, Cloudflare R2에 파일 2개.
